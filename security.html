Security Architecture & Controls

Operating autonomous AI agents against a financial backend requires rigorous defensive controls. Every mechanism below is implemented and enforced in the core engine codebase.

1. Cryptographic Cart Security (X-CSM-Cart-CSRF)

Every cart session is bound to an isolated cryptographic CSRF token transmitted via the strict X-CSM-Cart-CSRF HTTP header:

  • Generated at initial cart creation and rotated on every state mutation (add item, modify quantity, apply coupon).
  • Enforced at strict level — requests lacking a valid token are rejected before reaching inventory or order tables.
  • Prevents cross-session injection, cart hijacking, and request tampering across headless storefronts.

2. PCI-DSS Tokenization Boundary

CSM Engine never stores raw credit card credentials or sensitive cardholder data in plain text — at rest or in transit through the MCP layer. Card details are tokenized client-side via Stripe Elements or the PayPal SDK before hitting server infrastructure. CSM orchestrates payment intents, authorizations, and refunds without ever touching primary account numbers (PAN).

3. HMAC Webhook Signature Verification

Incoming payment webhooks are authenticated with dual-layer roundtrip signature checks (CSM_Stripe::check_webhook()). Every webhook's HMAC-SHA256 signature is verified against the gateway signing secret before processing. Events are idempotency-guarded to prevent duplicate order states or replayed transaction confirmations.

4. Token Storage & OAuth 2.1 PKCE Server

Agent authentication supports both static Bearer tokens and dynamic OAuth 2.1 flows:

  • One-Way SHA-256 Hashing: Static Bearer tokens are stored in the database only as SHA-256 hashes. Plaintext tokens cannot be extracted from database dumps.
  • OAuth 2.1 Server: Implements Proof Key for Code Exchange (PKCE), dynamic client registration, and RFC 8414/9728 discovery metadata (/.well-known/oauth-authorization-server).
  • Rate Limiting: Enforces 60 tool calls per minute per token to prevent agent runaway loops.

5. Two-Phase Dry-Run Approvals

Under the recommended approval_required permission mode, mutating tool calls do not commit immediately. CSM executes a dry-run simulation, generates a human-readable diff, and issues an ephemeral approval token bound strictly to the exact input arguments with a 600-second expiration window.

6. Credential Masking & Immutable Audit Trail

Sensitive gateway keys (Stripe secret keys, PayPal client secrets) are masked in MCP resource responses (settings_get returns masked values like sk_live_...9f2a). Third-party messaging tokens (e.g. WhatsApp access tokens) are stored encrypted.

Every mutating action, login event, and permission modification is appended to the dedicated relational table csm_audit_log (over 4,736 entries verified in reference production environments).

COMPLIANCE ARCHITECTURE NOTICE: CSM Engine's open-core codebase implements defensive engineering patterns aligned with PCI-DSS non-storage rules and OWASP API Security standards. However, because CSM is a self-hostable open-core software package, individual merchant deployments must manage their own server-level hosting certifications (e.g. SOC2, ISO 27001, PCI-DSS Level 1 AoC).
